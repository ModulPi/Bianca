## 1. 模块定位

### 1.1 一句话目标

> 用户用**对话**的方式给一个**交易目标**，由**经理 Agent** 理解目标、拆成任务、指挥手下的子 Agent（行情 / 分析 / 风控 / 执行）去干，并在过程中持续判断"离目标还差多少"，直到达成、放弃或到期。

本节是本文档存在的理由。此前全仓库（`docs/` + `agent/`）grep `目标 / goal / 经理 / 对话` 均为零命中 —— 这不是"少个功能"，是**这个能力没有被定义过**。本模块把它定义下来。

### 1.2 角色划分

| 角色 | 是谁 | 职责 | 现状 |
|------|------|------|------|
| **用户** | 人 | 提出目标、修正目标、必要时批准 | — |
| **对话层** | 交互通道 | 承载多轮对话；目标会话的边界 | ❌ 不存在 |
| **经理 Agent** | LLM 编排者 | 理解目标 → 分解任务 → 派活 → 收结果 → 判断进度 → 再决策 | ❌ 不存在 |
| **子 Agent** | 被调用者 | 执行具体动作并回报**可信**结果 | ⚠️ 三个节点存在，但不可被调用、结果不可信 |
| **数据面** | 独立进程 | 提供行情与指标 | ✅ 已独立运行（ADR-017） |

### 1.3 边界划分：做什么，不做什么

**做：**
- 一次会话承载一个目标的完整生命周期（提出 → 执行 → 达成/终止）
- 目标可被自然语言表达，也可在对话中被修正
- 经理层自己决定"下一步调哪个子 Agent"，而不是走写死的流水线
- 全过程可回溯：目标 → 分解的任务 → 每个子 Agent 的输入输出 → 结论

**不做（本模块范围外）：**
- 多用户 / 注册登录（PoC 约束，PRD D10 仅 localhost）
- 前端 UI 的实现（若做，属另一模块）
- 交易所接入本身的改造（属现有 exchange 模块）
- 数据面的采集逻辑（已有 ADR-017，与本模块只通过供数接口相接）

### 1.4 与现有 PoC 目标的关系

PRD v0.4 的 PoC 目标是「LLM 自主完成 1 买 1 卖闭环」（D2/US-P05），判定标准是**有没有产生订单**。本模块的目标是**一个更高的判定标准**：订单只是手段，要判定的是目标本身有没有达成。

两者不是替代关系，是叠加：
- PoC 闭环（已具备代码，尚未实测验收）→ 证明"能交易"
- 本模块 → 证明"能为了一个目标而交易"

**这意味着 PoC 的 `LLM_AUTO_EXECUTE` 布尔开关不足以承载本模块** —— 那个开关假设"自动"是全局的、无条件的；本模块要求授权是**会话级、随目标固化**的（ADR-018 / ADR-021）。

## 2. 目标形态

### 2.1 一次完整的交互长什么样（目标时序，草案）

```
用户 ──"我想用 1000 USDT 试水，两周内做到 1100，最多亏 5% 就停"──▶ 对话层
                                                                    │
                                                          ┌─────────▼─────────┐
                                                          │   经理 Agent      │
                                                          │ ① 解析目标        │
                                                          │ ② 复述确认 ◀──────┼──▶ 用户确认/修正
                                                          └─────────┬─────────┘
                                                                    │ ③ 拆任务
                                    ┌───────────────┬───────────────┼───────────────┐
                                    ▼               ▼               ▼               ▼
                              [行情子Agent]   [分析子Agent]   [风控子Agent]   [执行子Agent]
                                    │               │               │               │
                                    └───────────────┴───────┬───────┴───────────────┘
                                                            │ ④ 结果回传
                                                  ┌─────────▼─────────┐
                                                  │ ⑤ 进度判定        │
                                                  │ 达成? 破线? 到期? │
                                                  └─────────┬─────────┘
                                                            │ 未达成 → 回到 ③
                                                            ▼
                                                     ⑥ 汇报并收尾
```

关键：**③ 到 ⑤ 是一个循环，不是一条直线。** 现有实现（`build_trade_graph`）是一条从 START 到 END 的直线，每轮结束即终止，没有任何"回到上一步"的边。

### 2.2 目标的结构化表示（草案，待 §7 后定稿）

目标至少要有这些维度，否则"离目标还差多少"无法计算：

| 维度 | 例 | 缺了会怎样 |
|------|-----|-----------|
| 初始资金 | 1000 USDT | 无法算收益率 |
| 标的范围 | BTCUSDT（或"你选"） | 无法限定搜索空间 |
| 收益目标 | +10% | 无达成判据 |
| 回撤上限 | 5% | 无止损判据 |
| 时间窗 | 两周 | 无到期判据 |
| 授权级别 | 全自动，随目标固化（ADR-018） | 无执行边界 |

### 2.3 生命周期与终止条件

```
   proposed ──确认──▶ active ──┬──▶ achieved  （达成，是否平仓见 §7）
                               ├──▶ aborted   （破线：回撤触顶 / 用户中止）
                               └──▶ expired   （时间窗到期）
```

**目前这三种终止状态一个都没有。** 现有实现的终止条件是隐式的："这一轮跑完了就 END"。

**全自动下的补充要求（ADR-018）：** 三个终止判据必须由**代码**判定，不依赖 LLM 自觉。人是事前不参与、事后才到的，所以判据写死在执行路径上（回撤触顶 / 时间窗到期 / 预算耗尽），经理无权绕过。

### 2.4 可归因性（ADR-018 的连带硬需求）

用户原话：

> 经理能全权负责交易，但是要记录操作记录，做好每一笔交易的执行原因，以及相关数据，方便后期问题归因，以及迭代优化。

全自动把"记录"从一个加分项变成了**唯一的事后手段**。要求拆成三条可验收的判据：

| # | 判据 | 含义 |
|---|------|------|
| R1 | 每笔交易能回答"**为什么**" | 决策链路完整：目标 → 计划 → 当时的判断 → 信号 → 风控结论 |
| R2 | 每笔交易能回答"**当时看到了什么**" | 决策时刻的行情上下文被**完整**留存，不是摘要 |
| R3 | 每笔交易能回答"**当时手里有什么**" | 决策时刻的持仓、可用余额、权益、距目标的距离 |

**已核实：现状三条都不满足。** 证据（2026-10-11 读码）：

| 缺口 | 证据 | 后果 |
|------|------|------|
| A1 | `agent/storage/repository.py:124` 的 `save_signal` 签名收了 `market_data`，**函数体只用它取 `symbol` 和 `last`（:141、:144）**，整份行情快照丢弃 | R2 不满足 |
| A2 | `decision_logs.prompt_summary` 取自 `agent/llm/prompts.py:80-83` 的 `summarize_market_for_log()`，返回 `"BTCUSDT last=12345"` 一行 | R2 不满足 |
| A3 | `agent/market/repository.py:170` 的 `SnapshotRepository.save()` **零调用者**；`indicator_snapshots` 表自建表起从未写入 | R2 不满足（行情模块阶段二未开工的连带） |
| A4 | 无持仓、无权益快照；`_update_daily_pnl`（`agent/graph/execute_agent.py:95-108`）是名义近似 | R3 不满足 |
| A5 | `trade_logs` 有 `decision_id` 可关联决策，但**没有 goal_id / plan_id**，也没有"哪一步经理决策产生的" | R1 不满足 |
| A6 | `decision_logs` 存了 `raw_output`（LLM 原话）与 `parsed_signal`，但**不存完整 prompt** | R1/R2 部分不满足 |

**能看到的 vs 看不到的：** 现状能看到"LLM 说了什么"，看不到"LLM 当时看到了什么"。归因恰好死在这个缺口上 —— 而全自动模式下，这是唯一能查错的地方。

**设计含义：** 记录不是"顺手写个日志"，是这条产品线的**验收对象本身**。阶段 A 必须在动经理层之前先把 R1–R3 补齐（§6）。

**现状更新（2026-10-11，A-4 落地后）**

上面那张证据表是当时读码的记录，保留不动。逐条对应现在的状态：

| 缺口 | 现在 |
|------|------|
| A1 `save_signal` 丢弃行情快照 | ✅ 已修 —— 整份 `market_data` 落 `context`（`test_save_signal_keeps_the_whole_market_context`） |
| A2 只有一行 `prompt_summary` | ✅ 已补 —— `prompt_summary` 保留（给人扫一眼），归因依据换成 `prompt` + `market_data` 两列 |
| A3 `indicator_snapshots` 从未写入 | ❌ **仍未解决** —— A-4 把指标内联进决策记录，时间轴上的指标序列仍缺（行情模块阶段二） |
| A4 无持仓、无权益 | ✅ 已由 A-2a/A-2b 补上，A-4 又把**决策那一刻**的副本钉进 `trade_logs` |
| A5 无 `goal_id` / `plan_id` | ⚠️ **通道通了，没有生产者** —— 列在、`TradeState` 在、真跑整图的用例在，但目标实体是阶段 C 的活 |
| A6 不存完整 prompt | ✅ 已补 —— 存的是**实际发出**的 messages（含重试用的哪一份），超时那笔也留 |

所以逐条判据是：**R2 ✅ 满足 / R3 ✅ 满足 / R1 ⚠️ 部分**（链尾完整 + 完整 prompt；
"目标 → 计划"两段欠着）。核对方式与原始读数见 §6.3。

**这就是阶段 A 的验收口径**：R1 保持"部分"，直到阶段 C 有 goal 实体把它补满 ——
不因为"列已经建好了"就当它满足。

每一条都标了证据位置，便于逐个核。

| # | 缺口 | 证据 | 影响 |

| G2 | **Supervisor 是固定流水线，不是编排者** | `agent/graph/supervisor.py:80-94` 的 `build_trade_graph()` 是写死的线性图；路由是 Python 函数 `route_after_analysis` / `route_after_risk`（同文件 :64-77） | 没有"经理"这一层 |

| G7 | **风控只有 2 条** | `agent/risk/engine.py:15`：`[MaxTradeAmountRule(), DailyLossRule()]`，无止损/回撤/仓位 | 经理没有"保护本金"的手段 |
| G8 | **数据面未接入决策链** | `agent/graph/supervisor.py:19-30` 的 `fetch_market_node` 直连 ccxt 取 ticker + 25 根 1h K 线；术语表定义的供数接口 `get_market_context()` 全仓库无实现；`market.db` 的 477 万行只被健康检查 import 过 | 经理没有"看历史"的能力 |
| G9 | **控制面无法无人值守** | `agent/api/routes.py:103-116`：AgentRunner 只能由 `POST /agent/start` 在 API 进程内拉起；`agent/main.py` 的 lifespan 不启动它；守护机制只有数据面有（`agent/market/task.py`） | 经理一挂，目标执行中断且无人知道 |
| G10 | **没有通知出口** | 全仓库 grep `telegram / notify / alert / webhook` = 0 命中 | 达成/破线/失败无人知晓 |
| G11 | **授权是全局布尔** | `agent/config.py:28` 的 `llm_auto_execute` 是进程级开关，非会话级、不可撤回 | 见 §1.4 |

**缺口之间的关系：G5+G6+G7 是 G2 的前置。** 经理 agent 的能力上限等于它手下工具的能力上限 —— 工具给不出可信的持仓、回撤和执行回执，经理再会编排也只是在幻觉上调度。所以实现顺序上，**先补 G5/G6/G7，再建 G2**。

**再加一条（ADR-019）：G5/G6 同时是可归因性的前提。** R3"当时手里有什么"直接依赖持仓与权益，R2"当时看到了什么"依赖 `market_data` 不被丢弃 —— 也就是 §2.4 的 A1/A4 与这里的 G5 是同一件事的两个说法。**记录不是额外工作，是把 G5/G6 做对的副产品。**

## 4. 与现有模块的关系

### 4.1 控制面 vs 数据面

数据面已经独立成进程并有守护（ADR-017 缺口 1/2）。**本模块是控制面的重构，且控制面目前完全没有对应的独立运行形态** —— `AgentRunner` 仍是 API 进程内的一个 asyncio 任务。

经理模式让这件事更紧迫：经理若挂在 API 进程里，一次热重载就会中断一个正在执行的交易目标。

### 4.2 现有三节点的去向

| 现有节点 | 在经理模式下的角色 | 需要的改造 |
|----------|-------------------|-----------|
| `fetch_market_node` | 变成经理的一个**只读工具**（`query_market`） | 接供数层（G8） |
| `analysis_node` | 保持不变，作为**子 Agent** | 输入需带上目标与持仓上下文 |
| `run_risk_agent` | 保持不变，是**必经节点**（ADR-006 不变量） | 规则要能由目标派生（见 §7 问题 4） |
| `run_execute_agent` | 保持不变，作为**子 Agent** | 补对账与幂等（G6） |

原则：**子 Agent 保持确定性、可审计；不确定性只留在经理层。** 这既符合 ADR-006 的风控不变量，也让交易执行路径不受 LLM 自由度影响。

## 5. 关键风险与对策

| # | 风险 | 影响 | 对策 |
|---|------|------|------|
| 1 | **全自动 + 记录不全 = 无法归因**（决策 1 的直接后果） | 错误交易无人能拦，事后也查不出为什么 —— **这是本模块的头号风险** | 阶段 A 先补齐 R1–R3（§2.4）；记录不足时不得进入阶段 D |
| 2 | **单目标失控** | 循环不收敛，持续下单 | 硬性终止条件（回撤 / 时间窗 / 预算）必须是**代码级**的，不依赖 LLM 自觉（§2.3） |
| 3 | **LLM 编排放大调用次数** | 成本与延迟数量级上升；一次决策可能触发多轮 tool-calling | 设每轮预算上限 + 每目标总预算；`/usage` 已有汇总基础 |
| 4 | **本地模型不支持 function-calling** | 切到 Ollama 后经理层直接不可用（`deepseek-r1` 类推理模型的工具调用支持需实测确认） | **已实测（2026-10-11）：模型本身会调，挡住的是 Ollama 的模板/解析器 —— 见 §5.1** |
| 5 | **目标歧义** | "帮我赚钱" 无法转为判据 | 经理必须**复述确认**才能进入 active（§2.1 步骤 ②） |
| 6 | ~~经理越权改风控~~ | 用户说"这次放宽点"→ 经理自行调高上限 | ✅ **已由 ADR-021 缓解**：风控参数只能在目标确认那一刻一次性固化，执行期间经理只有读权 |

### 5.1 风险 #4 实测结果（2026-10-11，`scripts/check_llm_tools.py`）

**结论：模型完全会调工具，交付不出来的原因是 Ollama 的模板与解析器对不上。**

实测环境：`.env` 配的是 `LLM_PROVIDER=ollama` + `LLM_MODEL=deepseek-r1:latest`
（`LLM_API_KEY` 为空，云端路径未配置；本地模型库 `D:\LLM` 只有这一个 tag）。

**第一轮：它编了一个工具。**

| 查了什么 | 结果 |
|---------|------|
| Ollama 报的 capabilities | `['tools', 'thinking', 'completion']` —— **它说自己支持工具** |
| 真发一次带 `tools` 的请求 | HTTP 200，**`tool_calls` 条数 = 0** |

问题是"我现在手里有多少 BTC？只查一下，不要下单"，给了 `get_position`（只读）和
`place_order`（会动钱）两个工具。它没调任何一个，而是**凭空写了一段调用不存在的
`get_balance` 的 Python**，并接着"执行"了它，报出结论：**"你的当前BTC余额是：0.00 BTC"**。

**为什么这条比"不支持"严重得多：** 对一个交易经理层来说，"没有工具可用"会立刻露馅；
而**"假装用了工具、并编出一个数字"** 会被下游当成真数据。这不是理论风险 —— 它的
capabilities 里明明写着 `tools`，任何人照着 capabilities 写代码都会被骗。

**第二轮：按方案 A 往下拆，前两层的归因都被推翻了。**

| 层 | 原先的假设 | 实测结果 |
|----|-----------|---------|
| 模型是谁 | `deepseek-r1` 就是 DeepSeek-R1 系 | **权重是 Qwen3-8B**（`general.architecture=qwen3`，8.19B，Q4_K_M）。模型名是个假标签 |
| 根因在哪 | 模板漏了 `.Tools` 渲染块 | 对，但**改不掉** —— 见 ① |
| 模型会不会调 | 待测 | **会，而且挑得对** —— 见 ④ |

四次实测，逐条：

**① Modelfile 的 `TEMPLATE` 是死的。** 用同一个权重 blob 造了 `bianca-tools:latest`
（`FROM deepseek-r1:latest` + 一份带 `.Tools` 的模板），`ollama create` 成功、复用了原 blob、
**原模型没动**。但 `/api/show` 返回的模板与 `deepseek-r1:latest` **逐字节相同**（都是 2937 字
那份 DeepSeek Jinja 模板）—— 模板层被完全忽略。Ollama 0.34 的行为是「**GGUF 内嵌模板优先**」，
Modelfile 里写的模板不参与。附带踩到的坑：`ollama show --modelfile` 打印的是 **Go** 模板，
`/api/show` 返回的是 **Jinja** 模板 —— 两个引擎、两份内容，只看其中一个必然判断错。

**② 带上 `tools` 反而更糟 —— 会硬报 500。** 客户端把工具 schema 放进 system message、
但**不带** `tools` 数组：HTTP 200，模型给出完全正确的调用。把 `tools` 数组**加回去**：
**HTTP 500**，`llama-server chat error: ... does not match the expected peg-native format`。
即 **Ollama 一看到 `tools` 就启用按模板推导的 PEG 原生解析器**，而这个模型
`family=qwen3` 却揣着 DeepSeek 模板，两边对不上，解析器直接抛错。稳定复现三次。

**③ `OLLAMA_GO_TEMPLATE=1` 能让自制模板生效。** 这个环境变量在 `ollama.exe` 里存在
（但**没写进 `ollama serve --help`**）。带上它重启后：`bianca-tools` 的生效模板换成我们那份
1272 字的（含 `.Tools`），capabilities 变成 `['completion', 'tools']`；而 `deepseek-r1` 的
capabilities 掉成 `['completion', 'thinking']` —— **工具标签消失了，反而变诚实了**，
因为它的 Go 模板里确实没有工具块。

**④ 模板生效之后，模型看得见工具，但不肯按格式回。** 它读懂了工具清单（还判断出
`get_position` 是只读的、"不会动钱"），但输出是**散文 + 代码围栏**，没有 `<tool_call>` 外壳，
Ollama 于是解析出 0 条：

    好的，我将调用工具来查询当前账户的 BTC 持仓情况。请稍等片刻。

    ```json
    {"name": "get_position", "arguments": {"asset": "BTC"}}
    ```

**载荷完全正确，只是没穿那件外壳。** 补了「只输出下面这个块、不要别的东西」的强指令后
依然如此 —— 这是模型自身的输出习惯，不是提示词能拧过来的。

**所以：模型这一侧是通的，Ollama 这一侧是堵的。** 排除法之后，剩下三条路：

| 方案 | 做法 | 现在的把握 |
|------|------|-----------|
| **A. 修 Modelfile** | 造衍生 tag + 改模板（已实施：`bianca-tools:latest`） | **未打通。** 模板层默认被忽略，要靠**未文档化的服务端全局开关** `OLLAMA_GO_TEMPLATE=1` 才生效；即便生效，仍拿不到 `tool_calls`（见 ④） |
| **B. 工具描述塞进 system prompt** | 不传 `tools` 字段，schema 自己拼进 prompt，回什么格式就解析什么格式 | **已实测可行**（见 ②）：调用被完整拿到，选对只读工具、不碰会动钱的那个、参数正确。不依赖模型的 template 支持。代价是我们自己拥有解析器 —— 对交易系统反而是好事：可单测、可留痕、解析不出来就拒 |
| **C. 换模型 / 填云端 key** | 拉一个原生支持工具调用的模型，或给 `LLM_API_KEY` 填值 | 未动。最省事，但引入新依赖或花费，与本机"本地化"的取向冲突 |

**在拍板之前，阶段 B 不该动工** —— 整个阶段的形态取决于这个答案。

**后续（2026-10-11 同日晚些时候）：方案 C 被启用，本地模型线搁置。**
B-1/B-2 按方案 B 落地并全部通过后，用户决定**暂时改走 DeepSeek 官方 API**（`LLM_PROVIDER=deepseek`）。
本地模型每轮约 4 分钟（8 t/s），实跑一轮就要等好几分钟，调试成本过高 —— 这是搁置的实际理由，
不是方案 B 本身有问题。**Ollama 那条线没有作废**：§5.1 的四次实测结论仍然成立，
代码保留回退路径（见 §6.4.1）。本地 `ollama serve` 已停回接手前的状态（未运行）。

**遗留物（2026-10-11 已清）。** 曾经的 `bianca-tools:latest` tag 已用 `ollama rm` 摘掉 ——
它与 `deepseek-r1:latest` **共用同一个 5.2GB 模型层**（manifest 里那一层的摘要逐字节相同），
所以摘下它释放 **0 字节**，`deepseek-r1` 未受影响（已用 `/api/show` 验证仍可解析）。
方案 A 的 Modelfile 配方保留在 `scripts/Modelfile.bianca-tools`，配
`scripts/check_llm_tools.py` 一起，本地线要重启时照着 `ollama create -f` 即可。
临时探针目录 `.tmp-probe/` 已整个删除（其内容是可再生的探测脚本与变异测试备份）。

## 6. 阶段划分与验收标准（草案）

> 决策已拍板（§7），下表据此定稿。**阶段 A 吸收了两项**：可归因记录（§2.4，因 ADR-018 全自动而成为硬需求）与原有的持仓/PnL/风控/对账。

| 阶段 | 交付 | 验收 |
|------|------|------|
| **阶段 A：补手下 + 可归因**<br>（不涉及 LLM，可离线验证） | 持仓与权益重建 + 真实 PnL + 成交对账与幂等 + 止损/回撤风控 + **完整决策记录（R1–R3）** | ① 能从 demo 账户重放出正确持仓与盈亏；② 对账能识别部分成交与拒单；③ **任取一笔历史交易，能完整复现"为什么 / 当时看到什么 / 当时手里有什么"** |
| **阶段 B：经理只说不做** | 子 Agent 工具化 + 只读工具；经理输出**计划** | 给一个目标，经理产出可读的分解计划与理由，**不产生任何订单** |
| **阶段 C：对话层** | 会话 + 消息持久化 + 自然语言目标解析 + 可修正结构 | 多轮对话可修正目标；经理复述确认后才进入 active；会话重启后上下文不丢 |
| **阶段 D：闭环（全自动）** | 经理全权指挥下单，硬性终止条件生效 | 一个真实目标从提出到终止全程无人工干预；达成/破线/到期三种终止都能触发；全过程可归因 |
| **阶段 E：无人值守** | 控制面独立运行 + 守护 + 通知 | 重启机器后目标执行自动恢复；达成/破线有通知出口 |

**阶段 A 是唯一可以立刻开工的**：它完全独立于 LLM、可离线单测，且是阶段 B–D 的前置 —— 经理的能力上限等于它手下工具的能力上限（§3 结论）。

**A-1 订单账本与成交对账 —— 代码已落地，离线 46 项测试通过，线上已验证（2026-10-11）。**

| 交付 | 位置 |

**修掉的谎报（原实现的真实缺陷）：** `order.get("filled") or amount` 在交易所未给成交量时
拿**请求量**兜底 —— 一笔 0 成交的单会被记为 `filled`，而日亏熔断正吃这个数。
现在拿不到可信回执即 `unknown`，`unknown` 是终态且**阻断重放**。

**实现期发现（都属于"会静默出错"的默认值，共四类。前三条是离线阶段读码/测试发现，
第四条是线上验证发现的 —— 它推翻了一个假设，见 ADR-023）：**

1. **提交失败的性质不能用同一条路径处理。** 网络类异常（`RequestTimeout` /
   `ExchangeNotAvailable`）下交易所**可能已经收单**，记 `rejected` 会让人放心重放 →
   重复下单。故拆成 `rejected`（明确拒绝，可重放）与 `unknown`（下落不明，禁止重放），
   由 `classify_submit_error()` 判定。不认识就归 `unknown` —— 保守方向是**少下单**。
2. **幂等键必须是确定性的。** `new_client_order_id()` 由决策派生（`sha1(seed)[:28]`）
   而非随机：随机 id 下"崩在提交与落库之间"的重放会真的开出第二笔单，幂等键形同虚设。
3. **`_failure_state()` 曾把分类结果丢掉、一律返回 `failed`** —— 提交超时被报成
   "失败"，而它其实是 `unknown`，二者处置完全相反。**这个缺陷是测试抓到的，不是读码读到的**
   （`test_network_error_is_unknown_not_rejected`）。
4. **"把幂等键发给交易所，交易所就会去重"是错的** —— 线上实测推翻了它（见上方验证结果
   与 ADR-023）。前三条的代价是记错一个数，这条的代价是**重复建仓**：真金白银，且
   没有任何本地记录会显示异常。它也是"未验证 ≠ 验证过"最直接的一次兑现 —— 这个假设
   在离线状态下无论写多少测试都不会变红，因为假 ccxt 根本没有拒绝重放的能力。

**线上验证结果（2026-10-11，币安 Demo，代理已开）**

验证脚本 `scripts/verify_execution_live.py`。真单号 `72004389261`：市价买 BTC，
`quoteOrderQty=10.0` → 成交 0.00012 BTC @ 83050.01，实付 9.9660012 USDT。

| 项 | 结果 |
|----|------|
| `FILLED`→`filled`、`open`→`submitted` 状态映射 | ✅ 与交易所一致 |
| `filled / average / cost` 字段是否真被填充 | ✅ 存在且被正确读出 |
| 回执路径与对账（`fetch_order`）是否给同一答案 | ✅ 一致 |
| 端到端：落 pending → 提交 → 对账 → 落终态 → 联动 `trade_logs` | ✅ 全通 |
| 重放不产生第二笔（**向交易所查证**，非断言） | ✅ 同 cid 只有 1 笔 |
| 提交前的 cid 回查（已用 / 未用两条分支） | ✅ 分别认领 / 放行 |
| **对账轮询**（订单停在 `open` 再收敛） | ❌ **仍未验** —— 市价单不下 `open`，构造不出该场景 |
| 网络类提交失败 → `unknown` | ❌ 只能单测，无法安全地在线上触发 |

**推翻了一个假设（本次验证最重要的产出）：交易所不按 `clientOrderId` 去重。**

原设计假定"同一 cid 重复提交，交易所会认成同一笔单"。实测**两笔不同的交易所订单
带着同一个 cid 先后成交**（`72002941540`、`72002945169`）。再测清了边界：

| 前一笔的状态 | 同一个 cid 再提交 |
|--------------|------------------|
| **挂单中** | 被拒：`-2010 Duplicate order sent.` |
| **已成交**（市价单） | **被接受，真的开出第二笔** |

币安的 cid 唯一性只约束**当前挂单**。市价单瞬间成交、立刻离开挂单集合，id 当场释放
—— 而市价单正是我们唯一使用的类型。**交易所侧的去重对我们不存在。**

后果：挡住重复下单的一直只有本地账本，而本地账本挡不住两种情形 —— 崩在"提交"与
"写入交易所单号"之间（那笔已成交的仓位会失管），以及本地库丢失/重建。修复见 ADR-023。

**过程中花掉的钱要说清楚**：验证脚本那次"重复提交测试"真的重复下了单，Demo 账户花了
**20** USDT 而不是 10。这是上面那个结论的由来，不是脚本 bug。

**仍未验证（不得当作通过）：**

- **对账轮询**（订单停在 `open` 再收敛）构造不出来：策略只下市价单，市价单不经过 `open`。
  要验它得下一笔限价单，而那是另一条代码路径 —— 记为已知缺口。
- 网络类提交失败 → `unknown` 的分支仅单测覆盖，线上无法安全触发。

**核心决策（ADR-024）：持仓以交易所为准，账本只解释变动。**

开工前的实测：**本地 `orders` 表 0 行，而 Demo 账户里有 0.00449504 BTC。**
纯账本重建持仓，对这个账户从第一天就是错的 —— 重建出来的不是真实持仓。
所以两者分工：交易所回答"现在有什么"，我们的账本回答"哪些变动是我们造成的"。

**线上验证（2026-10-10/11 实跑）**

| 项 | 结果 |
|----|------|
| 权益 = 现金 + 持仓市值 | ✅ `9708.12 + 373.31 = 10081.44` |
| BTC 用的是**实盘**价（不是 demo 价） | ✅ 83050.0，取生产 REST |
| 账外差异逐资产列出 | ✅ BTC / USDC / USDT 全额账外（账本为空，符合预期） |
| 两次快照之间价格波动**不**触发账外告警 | ✅ 权益从 10081.4357 变到 10081.4110，notes 仍为空 |
| `POST` 与 `GET /portfolio` 说同一套话 | ✅ 在真服务上跑通，三条字段逐一相同 |

**实现期发现：**

1. **"取不到价"不能按 0 计。** 悄悄按 0 会让权益偏低而无人察觉 —— 与 A-1 的
   "拿不到回执就记 unknown"是同一条原则。现在排除并显式列入 `unpriced`，
   同时注明**该权益只是下界**。
2. **裸的账外差额没有信号。** 账本为空时账外是 100%（实跑确认），从第一天就满格，
   看久了没人看。真正说明"出事了"的是它**变了** —— 有东西在我们账本之外动钱。
   故 `unexplained_drift()` 报的是变化量；首次快照把整账户记为期初余额，不报异常。
   注意漂移按**数量**算而不是市值：否则价格波动会天天误报（已实测）。
3. **余额拉取需要重试。** 实跑时撞到一次 `load_markets()` 的 `RequestTimeout`（代理抖动），
   一次失败就让整张快照拿不到数。已按行情模块的同一套指数退避补上（3 次）。
4. **`unknown` 状态的订单不参与归因。** 它可能成交了也可能没有，按成交计入就是编数；
   不计入会让它落进账外差异里 —— 那正是我们希望被人看见的位置。

- 现金资产按面值 1:1 计价（USDC ≈ USDT），脱锚时权益有偏差。PoC 简化。
- **账外告警目前只是快照里的 notes 文本** —— 没有通知出口（阶段 E）之前，
  它需要有人去查 `/portfolio` 才看得见。

**A-2b 日亏熔断换成权益口径 —— 代码已落地，离线测试通过，线上已验证（2026-10-11）。**

| 交付 | 位置 |
|------|------|
| 日盈亏（纯逻辑 + 快照读取） | `agent/portfolio/pnl.py` |
| 熔断规则改用 `daily_pnl`（可为 None） | `agent/risk/rules.py::DailyLossRule` |
| 引擎接线 | `agent/risk/engine.py`、`agent/runner.py` |
| 每轮 tick 开头落快照 | `agent/graph/supervisor.py::_capture_equity_snapshot` |
| 现金流累加器**删除** | `execute_agent._update_daily_pnl` 已移除；`AgentConfigRepository.get_daily_pnl` 一并删除 |
| 线上核对脚本 | `scripts/verify_pnl_live.py`（只读；`--capture` 真抓，`--synthetic` 合成超限） |
| 测试 | `tests/test_risk.py`、`tests/test_portfolio.py`、`tests/test_execute.py` |

**为什么要换。** 旧实现 `_update_daily_pnl` 累加现金流，**把买入当成亏损**：花 100 USDT
买币，账上立刻记 −100，尽管那 100 变成了等值持仓；只能靠卖出时记 +100 抵消，
中间任何时刻的读数都不是盈亏。更糟的是它在**新的一天无条件返回 0.0** ——
那个 0.0 会被熔断读成"今天没亏"，于是熔断在当天第一笔单、也就是最需要它的时候是哑的。

**现在的算法**：`今天的盈亏 = 现在的权益 − 今天第一条权益快照的权益`，按 UTC 日切。
持仓浮亏自然含在内（权益已按市值计），这是用户 2026-10-11 的明确决定。

**线上验证（真实 Demo 账户 + 真实库）**

| 项 | 结果 |
|----|------|
| 权益快照能算出日盈亏（不是 None、不是编的 0） | ✅ 基准 10081.4356 → 当前 10081.4006，pnl = **−0.0349** |
| 基准取的是**当天第一条**，不是最近一条 | ✅ 当天 4 张快照里取最早那张 |
| 风控按这个数裁决 | ✅ 亏损在限内 → BUY 放行 |
| 减仓不被熔断拦住 | ✅ 同一时刻 SELL 放行（ADR-025） |
| 真抓一张快照（同 `capture()` 路径） | ✅ 条数 4→5，权益 10081.5255 |
| 熔断真的会跳（合成 −200 超 100 限额） | ✅ BUY 拦下且理由带上金额，SELL 放行 |
| 对外接口说的是同一个数 | ✅ `/agent/status.daily_pnl = −0.0349` |

**实现期发现：**

1. **"不知道"必须拦，不能放行。** 日盈亏算不出来时（当天还没有基准）返回 `None`，
   熔断拦下开仓并说明理由。把它当 0 会让熔断静默失效 —— 一个永远通不过的风控会被
   人发现，一个永远放行的不会。这是"交易所没说的，我们不编"在风控侧的同一句话。
2. **熔断只拦开仓（ADR-025）。** 收尾时发现原规则不看买卖方向：一触熔断连 SELL
   都拦，仓位被锁死在下跌里，熔断自身成了最大的风险源。改为只对 BUY 生效；
   单笔金额上限对双向仍然生效，风控依旧必经（ADR-006 不变）。
3. **快照失败不能让整轮 tick 崩。** `_capture_equity_snapshot` 吞掉异常只记日志：
   取不到快照的后果由风控承担（拿到"未知"→ 拦住开仓），这是一个**保守**的失败，
   比 tick 直接崩掉、什么都记不下要好。
4. **基准是"今天第一眼"而不是"昨天收盘"。** agent 若在盘中才启动，当日上限就从
   启动那一刻起算。这是可达信息里最诚实的选择；只要进程在跑，第一条快照总在
   开盘前或第一笔交易前产生，差别只在盘中启动的那一天。已记为已知偏差。

**仍未完成：**

- 快照是**每轮 tick 采一次**（默认 300 秒）。tick 间隔调大时，权益曲线会变稀。
- 权益为**下界**（有持仓取不到价时不计入），因此日亏也可能被低估 —— 方向是保守的，
  但要知道它偏在哪边。

### 6.2 A-3 止损/回撤 + 仓位上限 —— 已落地（2026-10-11 拍板并实施，304 个测试通过）

**开工前的硬约束（实测，不是推测）**

**我们拿不到可信的持仓成本价。** 交易所余额只说数量不说成本，本地订单账本是空的。
所以"跌到成本价 X% 止损"这件事对存量持仓**算不出来**。任何声称能算的写法都是在编数。

**行情库回答不了"近期高点"。** 实测 `data/market.db` 只有一条序列（BTCUSDT/1m），
最后一根 bar 是 **2026-09-24T14:32 UTC**，而当时是 2026-10-10T17:14 UTC —— **差了 16 天**。
采集器自 2026-10-09 起停摆。拿 16 天前的高点当"近期高点"，止损会算出一个和当下无关的数。

对策：**走生产 REST 的 `/api/v3/klines`**（与 `prices.py` 同一套 base_url + 代理）。
已实测可用：24 根 1h bar，真实 BTC，最高 83083.12。这条同时满足 ADR-013（行情取实盘）。

**决策（ADR-026 ~ ADR-029）**

| 决策 | 内容 |
|------|------|
| 止损基准 | **从观测到的近期高点回撤**，不用成本价 —— 对存量持仓同样成立 |
| 触发动作 | **拦开仓 + 系统强制平仓**；平仓路径不依赖 LLM，仍过风控与对账（不绕 ADR-006） |
| 仓位上限 | **单标的市值 / 权益** 的百分比 |
| 回撤基准 | **全历史峰值**，触发后需**显式重置**；回撤触发**清空全部持仓** |

**新增配置（`agent/config.py`）**

| 项 | 默认 | 含义 |
|----|------|------|
| `stop_loss_pct` | 0.10 | 单标的从近期高点回落多少触发止损 |
| `stop_lookback_hours` | 24 | "近期"的回看窗口（小时） |
| `max_drawdown_pct` | 0.05 | 权益从峰值回撤多少触发（PRD 的回撤上限） |
| `max_position_pct` | 0.50 | 单标的市值占权益的上限 |
| `force_close_enabled` | true | 强制平仓总闸 —— 会真的下单，留一个能关的开关 |

**新增数据输入**

- `EquityRepository.peak(since_iso=None)` —— 峰值；缺省是全历史，给了起点则忽略之前的。
  （计划里叫 `peak_since`，实现时改名：全历史是常态，给起点是例外。）
- `AgentConfigRepository` 存 `drawdown_reset_at`（复用已有的通用键值表）。
- `agent/portfolio/klines.py` —— 生产 REST 取近期 K 线并算高点，**只用已完成 bar**
  （与行情模块 `recent_closes` 的约定一致）。它只出"高点"这一半；现价取自最新权益快照的
  `position.price`，不在裁决时重新取价 —— 见下方"仍然做不到的"。

**风控侧**

`RiskContext` 增加 `equity` / `positions` / `peak_equity` / `highs`（均可为 None）。
新增三条规则：

| 规则 | name | 只拦 BUY？ | 触发动作 |
|------|------|-----------|---------|
| `PositionLimitRule` | `position_limit` | 是 | 拦开仓 |
| `TrailingStopRule` | `stop_loss` | 是 | 拦开仓 + 该标的全平 |
| `DrawdownRule` | `drawdown` | 是 | 拦开仓 + 全账户清仓 |

**算不出来时一律拦住开仓**（与 `DailyLossRule` 同一条原则）：拿不到高点、拿不到权益、
拿不到峰值 —— 保护不成立就不要开新仓。

**强制平仓路径（新建）**

1. 风控裁决时若带出 `force_close` 指令（标的 + 原因），由 supervisor 在图**之外**执行；
2. 平仓单是**合成的 SELL 信号**，走同一个 `run_execute_agent` —— 幂等键、先写库再提交、
   提交前回查、对账，一条都不少；
3. **强制平仓豁免 `MaxTradeAmountRule`**（否则仓位大于单笔上限时根本平不掉），
   但豁免要写在裁决里、落进 `risk_events`，不能是隐式的；
4. 平仓原因写进 `trade_logs` 与 `risk_events`，满足 ADR-019 的可归因要求。

**实施顺序（每步都能单独验证）**

**计划里被实测推翻的四处（重要的不是"做完了"，是这几处）**

1. **`EquityRepository.peak_since` 改名成 `peak(since_iso=None)`。** 计划里的名字暗示"必须给
   一个起点"，实际"全历史"是常态、给起点是例外。名字要读起来像默认行为。

2. **止损挂在风控规则里根本不会触发。** 规划时以为 `TrailingStopRule` 就够了，实现时才发现
   `RiskEngine` **只在有交易信号时**被叫到：LLM 回 HOLD 的那一轮，`route_after_analysis`
   直接走 `log_only`，风控节点不执行。而"行情在跌但模型没想买"恰恰是止损最该生效的时刻。
   于是破线判定被抽成 `agent/risk/monitor.py`，由 tick 独立驱动，与 LLM 无关 ——
   这是 ADR-027 那句"不依赖 LLM"落到代码上的**实际形状**。

3. **`stop_breaches()` 会把负持仓变成买单。** 首版过滤条件写成 `not pos.quantity`，
   数量为负时放行，产出一张 `quantity=-1.0` 的 SELL —— 负的卖单就是买单。
   改成 `pos.quantity <= 0`。（数量为负本就不该在这里处置，那是我们还不上的东西。）

4. **资金费/稳定币会被当成持仓。** 真实快照里有 `USDC 5000` 和 `USDT 4708`。
   核对脚本第一版拿全部持仓去取高点，于是向交易所要了 `USDTUSDT` 这个不存在的交易对，
   换回 400。产品侧本来是对的（`CASH_ASSETS` 与 `_stop_assets` 都排除了现金），
   错在脚本没有复用产品口径 —— 核对脚本必须用产品的那把尺子，否则量出来的不是产品行为。

**仍然做不到的（先说清，不装作有）**

- 存量持仓的**真实盈亏**依然不可知（没有成本价）—— 止损是"从高点回落"的语义，
  **不等于**"我这笔亏了 X%"。
- 行情库仍停在 9-24；A-3 不依赖它，但"数据面停摆"这件事本身还没解决（ADR-017 的活）。
- **回撤窗口还很浅。** 权益快照 2026-10-10 才开始攒，实测峰值**就是最新的一张快照**，
  回撤恒为 0。5% 的回撤线现在几乎不可能破 —— 不是逻辑不对，是没有历史可比。
  等快照攒够几天才谈得上"这条线有没有用"。
- **判回撤用的是快照那一刻的价**，不是裁决时的价。快照可能过去几十分钟（实测 23 分钟）。
  宁可滞后也不自相矛盾：事后能拿同一张快照复算当时的裁决。
- **重置的两个入口已补齐（ADR-030，收尾时完成）。** `POST /api/v1/risk/reset-drawdown`
  与 `python -m agent.risk reset-drawdown --reason "..."`，两者调同一个 `reset_drawdown()`。
  理由必填，且写一条 `risk_events`（`drawdown_reset`，含**重置前**的峰值与回撤）。
  CLI 已端到端手工跑过（空库读数为"未知"退出码 0 / 缺理由被 argparse 拦下退出码 2 /
  带理由重置成功 / 复读看到重置点）。

### 6.3 A-4 可归因记录 R1–R3 —— 已落地（2026-10-11 拍板并实施，319 个测试通过）

**为什么现在做。** ADR-019 把可归因性定成**硬需求**，并明确要求它在阶段 D（全自动闭环）
之前就位。§2.4 已核实 R1/R2/R3 三条**都不满足**，而 D 之前只剩 B、C 两个阶段。
换句话说，这是最后一个还能从容做它的阶段。

- [x] 6. 线上核对脚本 + 本表回填

### 6.4 阶段 B 设计 —— 子 Agent 工具化 + 经理计划（2026-10-11 拍板：走方案 B）

**验收（§6 表原文）：** 给一个目标，经理产出**可读的分解计划与理由**，**不产生任何订单**。

**技术路线已定为方案 B（客户端解析）**，依据是 §5.1 的四次实测：模型会调、挑得对，
但 Ollama 那条链路上 `tools` 字段换不来 `tool_calls`，而绕开它反而完全可用。
选 B 还有一层理由：**解析器归我们自己**意味着可以单测、可以留痕、解析不出来就拒单 ——
对一个要求「任取一笔交易都能复现为什么」的系统（ADR-019），这比把解析交给服务端更合适。

#### 模块 `agent/manager/`

| 文件 | 职责 |
|------|------|
| `schemas.py` | `Goal`（目标）、`Plan`、`PlanStep` |
| `tools.py` | `ToolSpec`（name / description / parameters / read_only / handler）+ `ToolRegistry` |
| `prompt.py` | 把工具清单渲染进 **system message**（方案 B 的形态；转向原生 `tools` 后作为回退保留，见 §6.4.1） |
| `parser.py` | 解析模型回的工具调用，支持多格式；**解析不出来就拒** |
| `loop.py` | 经理循环：目标 → 只读工具 → 计划 |
| `__main__.py` | CLI 入口 |

#### 三条硬规则（写进代码，不只是写在这里）

1. **解析不出来 → 拒，绝不当成「模型没调工具」糊过去。** 与仓库原则
   「交易所没说的，我们不编」同源：**看不清模型想干什么，就不往下走。**
2. **阶段 B 的工具集只有只读的。** 不是靠约定 —— `ToolRegistry` 拒绝注册会改状态的
   工具，`place_order` 这一层根本进不来（ADR-027 的拦截原则前移到这里）。
3. **必须能区分「在调工具」和「在给计划」。** 见下：两种都是 JSON，形状也像。

#### 解析器要认的形状（全部来自 §5.1 的实测输出）

| 优先级 | 形状 | 出处 |
|--------|------|------|
| 1 | 结构化 `message.tool_calls` | 换云端模型时才会出现 |
| 2 | DeepSeek 原生：`<｜tool▁calls▁begin｜>…<｜tool▁sep｜>NAME` + ```json 围栏 | 本地模型**不带 `tools`** 时实测产出 |
| 3 | 裸的 ```json 围栏 `{"name":…, "arguments":…}` | 本地模型**带 `tools`** 时实测产出 |

**判定「这是调用而不是计划」的条件（两个都要满足）：** JSON 对象的 `name` **命中已注册
的工具名**，且带 `arguments`。只有计划没有 `name` 的、`name` 不认识的一律不当调用 ——
否则会把一段计划当命令执行。这条要有专门的用例钉住。

#### 分步实施

| 步 | 内容 | 状态 |
|----|------|------|
| **B-1** | `tools.py` + `prompt.py` + `parser.py` | ✅ 落地（25 项离线用例） |
| **B-2** | 只读工具集（7 个：账户快照 / 行情 / 风控参数 / 回撤 / 决策 / 成交 / 风控事件） | ✅ 落地（23 项用例，两个临时库） |
| **B-3** | `loop.py` + `Plan` + 入口 | ✅ 落地（13 项离线用例，全量 380 通过）；**随后按 §6.4.1 转向原生 `tools`** |

**B-1 / B-2 实测结果（2026-10-11，全量 367 通过，`data/bianca.db` 与 `data/market.db` 均未被写入）**

**判据本身被拆过两次才发现没用。** 「`name` 命中已注册工具 **且** 带 `arguments` 才算调用」
这条判据，最初写了两个用例去钉它，**把判据拆掉却全绿**：

1. 第一版用例的计划里写 `{"name": "我的计划"}` —— 靠更早的「name 必须命中已注册工具」
   就被刷掉了，压根走不到 `arguments` 那道闸。
2. 第二版的 `name` 嵌在 `steps` 里 —— 而 `_iter_json_objects` 只吐**最外层**对象，
   还是走不到。

第三版才用上「顶层就带真实工具名、但没有参数」的形状（含 OpenAI 的嵌套变体），
拆掉判据后**正好这两条红**。**一个钉不住东西的用例比没有用例更糟** —— 它让人以为
这里是有人看着的。

**回撤那一版重造轮子，漏了重置点。** 第一版 `get_drawdown` 自己用「全历史最高」算，
看起来更直白，但漏掉 ADR-029/030 的**重置点**：重置之后峰值只从那一刻往后看，
照搬全历史会算出一个虚高的回撤 —— 而风控引擎用的是 `pnl.drawdown()`，
于是**同一个概念出现两个口径**（经理据此定计划、风控据此开闸）。
已改为直接复用 `pnl.drawdown()`，并补一条「重置后峰值不再作数」的用例
（改回全历史，该用例变红，已实测）。

**「不知道」与「是 0」在工具层是两件事。** 快照没采过、行情库里没有这个 symbol ——
一律返回 `{"available": false, "reason": …}`，**不给 0、不给空列表**。有空库时
`equity` 这个键**根本不出现**，专门有用例钉住这一点。反例也钉了：只有一张快照时
回撤确实是 `0.0`，那不是「不知道」，不该报 unknown（口径跟 `pnl.drawdown()` 走）。

#### 6.4.1 B-3 转向：DeepSeek 官方 API + 原生 `tools` 字段（2026-10-11 拍板）

**B-3 写完之后、真模型实跑之前，用户改了两个前提：**

1. **后端换 DeepSeek 官方 API**，本地 Ollama 线暂时搁置（理由见 §5.1 末尾）。
2. **工具调用改回原生 `tools` 字段** —— 不再走方案 B 的自解析主路径。

**为什么这次可以改。** §5.1 里 `tools` 字段失败是 **Ollama 那条链路**的毛病（llama.cpp 的
PEG 原生解析器与 GGUF 内嵌模板对不上），不是 `tools` 这个协议本身的毛病。DeepSeek 官方
API 的 function calling 是成熟的。**换后端之后，绕行的理由消失了。**
**§5.1 的结论不作废** —— 它记录的是「在本地模型上会怎样」，回退时仍然有效。

**B-3 在转向前的状态（已完成，保留）：** `loop.py` + `schemas.py` + `__main__.py`，
13 项离线用例（脚本化 chat，不出网），全量 **380 通过**，两个真实库均未被写入。
三个判据各拆过一次确认用例真的会红：工具失败时塞假结果、`_http_chat` 里加 `tools`、
轮次用尽时硬凑计划。另外补了一条实测发现：

> **连不上模型 ≠ 模型没给计划。** 本地模型 8 t/s，120 秒超时是常态，最初撞出来的是
> 一个裸 traceback。现在 `httpx.HTTPError` 被循环捕获、**只报一次就停**（硬撑满 6 轮
> 只会让用户白等 6 个超时），错误文案是「跟模型说话失败」，**不含**「N 轮之内没拿到计划」。
> 这两句混成一句等于替模型背锅：事后归因时会以为「它想过了但没想出来」，
> 而事实是根本没问上。

**转向后要改的地方（B-3 收尾）：**

| 改动 | 内容 |
|------|------|
| `_http_chat` | 带上 `tools=registry.schemas()` 与 `tool_choice="auto"` |
| `ToolCall` | 增加 `id` —— 回 `role: "tool"` 时 `tool_call_id` 必须对得上 |
| 循环 | 结构化通道下，**assistant 那条消息要原样带上 `tool_calls`**（服务端按 `id` 配对） |
| 解析器回退路径 | `deepseek` / `fenced` 两种旧形状**保留**（Ollama 回退用），但它们产生的调用没有 `id`，此时观测结果改以 `role: "user"` 加前缀回给模型 —— **不伪造 `tool_call_id`** |

**验收不变：** 给一个目标，经理产出可读的分解计划与理由，**不产生任何订单**。

#### 6.4.2 B-2 的一个漏洞：工具只报数，不报「这数有多旧」（2026-10-11 补）

**怎么发现的。** 准备 B-3 真模型验收时先查了本地数据实况：

| 数据 | 最新一条 | 距今 |
|------|----------|------|
| `market.db` BTCUSDT 1m K 线 | 2026-09-24T14:32Z | **16.2 天** |
| `bianca.db` decision_logs / trade_logs | 2026-08-02T16:01Z | ~70 天 |
| `bianca.db` equity_snapshots | 2026-10-10T17:06Z | ~1 天 |

而 `get_market` 对 16 天前的 K 线照常返回 `{"available": true, "last_price": …}`，
`change_pct` / `sma20` / `rsi14` 一应俱全 —— **模型没有任何线索能看出这是陈的**，
只会当成现价去做计划。这和 §5.1 那个「编造 `get_balance` 并报出 0.00 BTC」是同一类：
**下游拿到的是一个数字，不是一句猜测，所以没人会去质疑它。**

**根因不是「少了个字段」，是判据没有复用。** 数据面早就有权威的新鲜度判定
（`agent/market/collector.py` 的 `_flow_verdict` + `_stale_after_s`，`/health` 与
`/market/status` 都由它出结论），但经理这条线自己去读库、自己算摘要，**绕过了它**。
这与 §6.4 里「回撤那一版重造轮子」是同一个毛病：同一概念迟早会分裂成两个口径。

**改法：**

1. 把采集侧那段判定提取成公开的 `symbol_flow_verdict(symbol, interval, settings=…)`，
   `market_health` 改为调它 —— **判据只有一份**，`/health` 与经理拿到同一个答案。
2. `get_market` 的返回值加上 `data_status`（ok / warming_up / error）、
   `data_status_detail`、`data_lag_seconds`、`stale`，并在停更时给一句 `note`。
3. 工具描述里写明「**先看 `data_status`，这份数据可能是停更的**」——
   光给字段不够，得让模型知道该看。
4. `get_portfolio` 同理补 `age_seconds`（快照表的节奏不由 `_stale_after_s` 管，
   所以这里**只报事实、不编阈值**）。

**阈值不新造。** `_stale_after_s` 已经是 `max(180s, 3 个周期)`，且带着一条实测教训
（固定 180s 会让 1h 周期有 94% 的时间误报）。再拍一个数只会多一个口径。

#### 6.4.3 B-3 真模型验收实录（2026-10-11，DeepSeek 官方 API）

**验收通过。** 目标「把回撤控制在 5% 以内，仓位别超过一半」→ 4 轮，产出完整计划
（目标复述、6 条带依据的步骤、7 条终止条件、4 条前提假设、6 条风险）。
账：`prompt 8360 / completion 1871 / total 10231`，其中缓存命中 7680。

**但 §6.4.1 那个前提被证伪了 —— 模型不用 `tools` 字段。**

为此在 `ManagerRun` 加了一栏 `shapes`（每轮模型回的是哪种形状），第二次跑出来是：

```
每轮形状  ['deepseek', 'deepseek', 'text', 'text']
```

**两轮工具调用全部是 `deepseek` 形状** —— 即模型把调用写在 `content` 正文里
（`<｜tool▁calls▁begin｜>…`），**没有用 `tool_calls` 结构化字段**，尽管我们如实发了
`tools` 与 `tool_choice=auto`。也就是说：

- **绕行的理由并没有随换后端而消失。** §6.4.1 说「`tools` 失败是 Ollama 链路的毛病、
  换官方 API 就该好了」—— 对 `deepseek-flash` 不成立，它直接忽略这个字段。
  **方案 B 的客户端解析器才是真正在扛整件事的那一层**，从 B-1 到现在都是。
- **回退路径已被真实调用验证。** 因为 `shape != "structured"`，服务端从不给调用号，
  `ToolCall.id` 恒为 `None`，于是工具结果一律走 `role: "user"` + 「工具 X 的结果：」前缀
  回给模型 —— 连跑 4 轮，模型接得住。**当前 `role: "tool"` + `tool_call_id` 那条分支
  是死代码**（留着的意义是"换到真会填 `tool_calls` 的模型时能自动生效"）。
- **`max_tokens=2048` 会截断原生格式的调用块。** 第一次跑时第 1 轮正文被从中间切断
  （`…get_risk_li`），解析器**照设计拒了**（看得见标记、解不出载荷 → 报错），
  循环把错误回给模型，第 2 轮它改对了。**这就是「解析不出来 → 拒，不当成没调工具」
  这条硬规则第一次在真实故障下生效**，而且救回了一整轮。第二次跑同样参数没再复现 ——
  属偶发，不该只靠运气。

**这条修复自己也得到了验证。** 计划第 1 步直接引用了 §6.4.2 补的字段：

> 暂停一切新增仓位，直到 `get_market` 返回 `stale=false`。依据：本地行情已停更
> 1397991 秒（约 16.2 天），`last_price` 84800.02 / RSI14 71.83 / SMA20 84448.69
> 全部是那一刻的读数。

第 2 步用的是 `get_portfolio` 新加的 `age_seconds`。第 4 步还做实了算术：
「仓位 = 50% 权益时，10% 止损一次就打掉 5% 权益，正好把回撤线打满，缓冲为零」——
没有 §6.4.2 那一改，同一个模型会拿 16 天前的价格当现价来定入场。

**已决：`tools` 字段留着，不换模型。** 三个选项里选「留着 + 文档写实」——
它几乎不要钱（这段 prompt 命中缓存），而换成真会填 `tool_calls` 的模型时
`_parse_structured` 那条通道会自动生效，不必改代码。代价是**得把「它其实不管用」
写清楚**，免得后来人照着 §6.4.1 的旧说法做决定：这件事在 `loop.py::_http_chat`
的 docstring 和 §6.4.1 的订正里各写了一遍。**留着的是可能性，不是能力。**

### 6.5 阶段 C 设计 —— 对话层（2026-10-11 拍板，实施中）

**C 要解决的一件事：把「目标」从一个字符串变成一个实体。**

B 的入口是 `Manager.plan(goal: str)` —— 收一句话，出去一个计划，**中间什么都不留**。
所以 `goal_id` / `plan_id` 到现在没有生产者（§6.3），R1 的链头是空的（§2.4）。
C 补的就是这一段：让目标有 id、有状态、有原话、有结构化结果，能被修正，能追溯到计划。

**边界重申（一条都不新开）：**

| 约束 | 来源 | 在 C 里的含义 |
|------|------|--------------|
| 自然语言为主、结构化为准 | ADR-020 | 解析 + **复述确认**，两者都要，缺一不可 |
| 风控参数在确认时一次性固化 | ADR-021 | `active` 那一刻抄一份进目标行，之后只读 |
| 交互只做 CLI/HTTP | ADR-022 | 端点 + 薄 CLI，验收要给可复制的命令序列 |
| **C 不下单** | §6 阶段表 | C 的终点是「一个有计划的 active 目标」，不是一笔成交 |

#### C-1 目标实体与会话（离线可测，不碰模型）

- 新表 `goals` 与 `messages`：一个 session 承载一个目标（一次一个，§8 第 3 条倾向），
  消息按 session 挂。**会话重启不丢上下文，靠的就是这张表**（验收第 4 条）。
- 字段从 §2.2 那六维来，**每个都可空**：用户没说的就是 `None`。
  「用户没说本金」和「用户说本金 1000」是两件事 —— 同 `readonly.py::_unknown()` 那条规矩。
- 状态机照 §2.3：`proposed → active → {achieved, aborted, expired}`，每次迁移留时间戳与理由。
- **风控快照是 ADR-021 的落地判据。** `active` 那一刻把 `Settings` 里那几个参数抄进
  目标行（`risk_snapshot`），**之后凡是读风控的地方都读这一份，不读 `settings`** ——
  否则「执行期间只读」只是句口号：改一次 `.env` 就绕过去了。
- 可归因：目标行记 `raw_text`（用户原话）+ `parsed`（结构化结果）+
  `proposed_at` / `confirmed_at` / `ended_at` / `end_reason`。

#### C-2 自然语言 → 结构化目标（解析 + 复述，用模型）

- 输入：会话历史 + 这句话；输出：`GoalDraft`（同 C-1 字段，拿不准的留空）。
- **缺字段不补默认值，在复述里点名问。** 「你说最多亏 5% 就停，但没说本金拿多少、
  打算做多久」—— 而不是替它填 1000 / 两周。填了默认值，"离目标还差多少"
  就是拿一个用户没同意过的数字算出来的。
- 解析结果本身也入记录（ADR-020 的代价条）。
- 复杂度兜底：数字走确定性抽取，语义交模型 —— 见待拍板 3。

#### C-3 多轮修正

- `proposed` 期间：用户说「回撤放到 8%」→ **只改这一个字段**，其余原样保留，
  然后重新复述。这就是验收里的「多轮对话可修正目标」。
- `active` 之后：**不能改。** 要改只能 `abort` 当前目标、重新提一个（ADR-021）。
  这条要有测试钉住 —— 否则「固化」会被一个方便的 PATCH 端点绕过去。

#### C-4 计划落库（补满 R1 的链头）

- 目标 `active` 之后调 `Manager.plan()`，把 `ManagerRun` 落库：`plan_id` +
  完整 transcript（R1 要的是**完整 prompt**，B 已经留了）。
- 从此 `decision_logs` / `trade_logs` 的 `goal_id` / `plan_id` **有生产者**，
  R1 由「部分」转「满足」（§2.4 的判据）—— 但要在 §2.4 那张表上改口径，不能默默算数。
- 顺带定 §6.3 那条遗留：止损强平那条记录认不认领目标。见待拍板 4。

**验收怎么跑（照 §6 阶段表）**

1. 提目标 → 经理回问缺的字段 → 补齐 → 经理复述 → 确认 → `active`；
2. 未确认时改一个字段 → 复述随之变；
3. `active` 后试图改 → 被拒；
4. 重启进程 → 会话历史仍在，接得上。

**这四条全部离线可测**（脚本化 chat + 本地库），一辆车都不出网。
真正要花钱的只有「真模型解析得准不准」那一条 —— 按既定口径，留在最后冒烟测试时再花。

**这 4 项已拍板（2026-10-11）**，各自的理由与否定方案见 §7：

| # | 问题 | 决定 | ADR |
|---|------|------|-----|
| 1 | 会话载体 | HTTP 端点为主，CLI 只做薄壳 | ADR-032 |
| 2 | 「初始资金」口径 | 以激活时的**实际权益**为准；口述数字另存一栏，只作校验 | ADR-033 |
| 3 | 解析策略 | 数字走确定性抽取，语义交模型 —— 两层分工要有明确分界 | ADR-034 |
| 4 | 强平记录是否认领目标 | 认领，但带 `origin="risk_force_close"` 与 LLM 决策区分 | ADR-035 |

#### C-1 已落地（2026-10-11，离线 21 项测试通过）

| 交付 | 位置 |
|------|------|
| 目标状态机（`proposed → active → {achieved, aborted, expired}`）| `agent/dialogue/goal.py` |
| 草稿与「缺哪个维度」的判定（`GoalDraft.missing()`）| 同上 |
| 风控快照（ADR-021 的落地判据）| 同上 `risk_snapshot()` |
| `goals` / `messages` 两张表 | `agent/storage/models.py` |
| `GoalRepository` / `MessageRepository` | `agent/storage/repository.py` |

**三条规矩各有测试钉着，且都做了变异检验**（拆掉逻辑，对应测试确实变红）：

1. **`0` 不算「没说」。** `_blank()` 若写成 `not value`，「回撤上限 0」会被读成沉默
   （`test_zero_is_a_stated_value_not_a_silence` 立刻红）。判空只认 `None` / 空串 / 空列表。
2. **`active` 之后写不进去。** `GoalRepository` 故意没有通用 `update()`，能写这一行的
   只有 `save_draft`（仅 `proposed`）/ `activate` / `end` 三个动作 ——
   「只读」靠**没有那个方法**保证，不靠调用方记得先查状态。
3. **终态就是终态。** `proposed` 不能直接到 `achieved`：一个从没执行过任何东西的
   目标不该有达成记录。这条是写测试时才被状态机教育的 —— 我原本让一个
   `proposed` 的目标「时间窗到期」，被 `check_transition` 顶了回来，**它拒得对**。

另外，`symbols` 在库里是 JSON 文本，读回来时**坏了不许退回 `None`** ——
`None` 的含义是「用户没说标的范围」，而真相是记录坏了，把后者说成前者等于
替一条烂记录编个合理的解释（`test_a_corrupt_symbols_column_is_not_read_as_user_silence`）。

#### 写 C-1 时撞上的冲突：用户说的回撤上限，和配置里的那个，谁说了算？

**ADR-021 只说了一半**：它定的是「风控参数在确认时固化、执行期间只读」，
没定「用户能不能在确认时改设定值，以及能不能改得**更宽**」。
`goals.max_drawdown_pct`（用户说「最多亏 5%」）与快照里的同名值（`.env` 里的 3%）
是同一个数的两个来源，C-1 第一版只抄了 `Settings`，用户那个数没进快照。

**已拍板（ADR-036）：取更紧的那个。** 落地时改了一处结构 —— 快照**在
`activate()` 里面现算**，不再接受调用方递一份现成的进来。理由是这类规则怕的不是
写不出来，是**被人绕过**：只要 `activate()` 还收一个现成的字典，谁哪天忘了把
目标里那个数带上，规则就静默失效，而失效的表现是**风控被放宽，不是报错**。
变异检验专门验了这一点（把 `stated_drawdown` 换成 `None`，风控线静默从 2% 放宽
到 5%，一个错都不报 —— 测试抓住了）。

## 7. 能力边界决策（ADR-018~036，2026-10-11 拍板）

> v0.1 曾在此列出四个待决问题。**四条已全部拍板**，记录如下。ADR 编号接续行情模块（ADR-007~017），上位架构文档的 ADR-001~006 暂未合并。

### ADR-018: 经理 Agent 全权负责交易

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 经理 Agent 有完整下单权限，**不设人工闸门**（非"计划批准制"、非"逐笔确认"）。授权随目标一次性固化。
- **理由:** 用户明确要求全权；目标是让 Agent 真正自主，人工闸门会把经理层退化成信号推送。
- **代价（用户已知悉并要求补偿）:** 出错时无人能在事前拦下。**因此本条强制绑定 ADR-019** —— 全权的前提是完整的可归因记录。
- **替代方案:** 计划批准制 / 逐笔确认 —— 均被否。
- **对现有设计的冲击:** `LLM_AUTO_EXECUTE`（`agent/config.py:28`）是**进程级**开关，无法表达"某个目标下全权、另一个目标下不"。阶段 C 引入目标对象后，该开关应由会话级授权取代；迁移期需明确二者优先级。

### ADR-019: 可归因性是硬需求

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 每笔交易必须留存足以回答三问的记录 —— **为什么（R1）/ 当时看到了什么（R2）/ 当时手里有什么（R3）**，详见 §2.4。
- **理由:** 用户原话"方便后期问题归因，以及迭代优化"。ADR-018 全权之后，这是唯一的事后手段；同时它也是"迭代优化"的数据来源。
- **代价:** 记录体积上升（完整上下文 vs 一行摘要）；需要给记录定保留策略与体积上限。
- **约束:** **阶段 A 未补齐 R1–R3 前，不得进入阶段 D（全自动闭环）**。这不是流程洁癖 —— 全自动 + 记录不全，等于把"出错"变成"不可查"。已核实现状三条全不满足（§2.4 证据表）。

### ADR-020: 目标以自然语言为主、结构化为准

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 用户用自然语言表达目标；经理 Agent 解析为**结构化目标对象**并复述确认；用户可在对话中修正结构字段。
- **理由:** 自然语言负责交互，结构化负责落库与"离目标还差多少"的计算 —— 两者承担不同职责，不冲突。
- **代价:** 多一层解析，且解析可能出错 → 用"复述确认"作为把关点（§2.1 步骤 ②）。解析结果本身也要入记录（ADR-019）。

### ADR-021: 风控参数仅可在目标确认时一次性授权

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 风控参数（回撤上限等）在目标确认那一刻随目标固化；**执行期间经理只有读权，不可修改**。要改必须中止当前目标、重新确认。
- **理由:** 防"用户随口说放宽点 → 经理自行调高止损"这条路径（§5 风险 6）。风控一旦可被被约束者修改，它就不再是边界。
- **替代方案:** 经理可自主调整 —— 被否，理由同上。

### ADR-022: 交互载体先只做 CLI/HTTP

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 阶段 C 的对话层以 HTTP/CLI 为载体，**不做 Web 前端**，延续 PoC D8。
- **理由:** 把精力放在经理层本身；前端属 MVP。
- **代价:** 对话体验靠 curl，验收时需给出可复制的命令序列。

### ADR-023: 幂等由本地账本 + 提交前回查保证，不依赖交易所

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11（线上实测后）
- **背景:** 实测推翻"交易所会按 clientOrderId 去重"的假设 —— 币安的 cid 唯一性只约束
  **当前挂单**，市价单成交后 id 立即释放，同一 cid 再提交会被接受（§6.1）。
  市价单是我们唯一使用的类型，故交易所侧**没有**去重。
- **决策:** 重复下单的防线是我们自己的，两道：① 本地 `orders` 表按 `client_order_id`
  唯一，且**先写库再提交**；② 提交前用 `fetch_order(origClientOrderId=cid)` 回查交易所，
  查到就**认领那笔**、不再提交。
- **理由:** ① 单独不够 —— 挡不住"崩在提交与写入交易所单号之间"（那笔已成交的仓位会
  失管）和本地库丢失/重建。回查把这两种情形从"放弃仓位"变成"找回仓位"。
- **代价:** 每笔单多一次网络往返。回查失败时**拒绝下单**（保守方向：少下单而非多下单），
  该轮记账但不落终态，下一轮再试。
- **替代方案:** 只用本地账本、把"交易所会去重"的说法从文档删掉 —— 被否，理由是留着一个
  已知会重复建仓的窗口，与 ADR-018 的全权自动交易不匹配；改下限价单让 cid 持续占用 ——
  被否，与策略要求的市价成交冲突。

### ADR-024: 持仓以交易所为准，账本只解释变动

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **背景:** 实测发现本地 `orders` 表 0 行，而 Demo 账户持有 0.00449504 BTC ——
  账户的余额大部分不是本 agent 造成的（上线前的余额、人工操作）。
  纯用账本重建持仓，对这个账户从第一天就是错的。
- **决策:** 持仓与权益取**交易所**的数（余额 u 交易所，价格取实盘，ADR-013）。
  本地订单账本只回答"哪些变动是我们造成的"。两者逐资产对比，
  差额显式记为**账外持仓**，不抹平。
- **理由:** 交易所是持仓的真相来源；账本永远只是关于**变动**的解释。
  把两者混成一个数，就再也分不清"策略亏了"和"账户里本来就有别的币"。
- **代价:** 需要处理账本与交易所的长期不一致；手续费（以基础币收取，实测）会造成
  持续的小额漂移。这些都必须被显式记录而不是修正掉。
- **替代方案:** 纯账本重建 —— 被否，实测已证明对本账户失真，且需要"初始快照"
  把存量持仓申报进来，多一个必须有人维护的输入。只做只读权益不做归因 ——
  被否，那样分不清权益变化是策略造成的还是外部造成的（ADR-019 要求可归因）。
- **配套:** 账外差额本身没有信号（账本为空时必然 100%），故只对它的**变化量**告警。
  漂移按数量而非市值计算 —— 否则价格波动会天天误报。

### ADR-025: 熔断只拦开仓，不拦减仓

- **决策:** 日亏熔断（以及"日盈亏未知"）只对 **BUY** 生效。SELL 单放行。
- **理由:** 熔断的目的是"别再加大风险"，不是"不许逃跑"。若把 SELL 也拦下，
  触及熔断后仓位就锁死，只能看着它继续跌 —— 熔断自身成了最大的风险源。
  这个缺口是 A-2b 收尾时才暴露的：原 `DailyLossRule` 根本不看买卖方向。
- **边界:** 放行 SELL **不等于**风控被绕过。单笔金额上限对双向都生效，风控仍是
  Execute 的唯一前置（ADR-006 不变）。仓位上限与止损是 A-3 的事。
- **替代方案:** 一律拦到当天结束 —— 被否，语义虽最保守，但代价是行情继续恶化时
  无法离场，把"保守"变成了"更大且不可控的敞口"。
- **配套:** 方向判断放在规则最前面，两条拒绝理由（未知 / 超限）都只针对 BUY。

### ADR-026: 止损基准是"从观测高点回撤"，不是成本价

- **决策:** 单标的止损用"该标的从**观测到的近期高点**回落 X%"判定，基准取实盘近期
  K 线（生产 REST `/api/v3/klines`，只用已完成 bar）加当前观测价。**不使用成本价。**
- **理由:** 我们**拿不到可信成本价** —— 交易所余额只说数量，本地订单账本为空。
  任何声称能算"这笔亏了多少"的写法都是在编数。而观测高点对**存量持仓同样成立**，
  因为它不依赖我们有没有经手过这笔仓。
- **代价（明说）:** 这是移动止盈损的语义，**不等于**"我这笔亏了 X%"。持仓期间该标的
  如果先涨后跌，止损位会跟着抬上去 —— 这是特性，但要知道它不回答"盈亏"。
- **否定方案:** 只用成交回执里的成交均价 → 对存量持仓完全无保护（账本为空）。
- **取数来源:** **不用行情库**。实测 `data/market.db` 最后一根 bar 停在 2026-09-24，
  比当时落后 16 天（采集器自 2026-10-09 停摆），拿它算"近期高点"会得出与当下无关的数。

### ADR-027: 触发后拦开仓 + 系统强制平仓，平仓路径不依赖 LLM

- **决策:** 止损/回撤触发时，系统既拦住新开仓，也**自己发起平仓**。平仓单是合成的
  SELL 信号，走与普通交易**同一个** `run_execute_agent`：幂等键、先写库再提交、
  提交前回查、对账，一条都不少。
- **理由:** 紧急出口如果依赖 LLM，就在最需要它的时刻最不可靠 —— LLM 可能超时、
  可能回 HOLD、可能根本没被调度到。保护动作必须在 LLM 之外也能成立。
- **不绕 ADR-006:** 合成的 SELL 仍过风控（ADR-025 下减仓本就放行），
  且平仓结果照常落 `trade_logs` / `orders` / `risk_events`。
- **豁免（必须显式）:** 强制平仓豁免 `MaxTradeAmountRule` —— 否则持仓市值大于单笔
  上限时根本平不掉，"保护"变成空话。豁免理由写进裁决与 `risk_events`，不做隐式放行。
- **否定方案:** 只拦开仓、把平仓留给经理 Agent（阶段 B）→ 被否，那意味着阶段 B 落地前
  触发后仓位一直挂着，没有任何保护。

### ADR-028: 仓位上限用"单标的市值 / 权益"的百分比

- **决策:** `max_position_pct`（默认 0.5）：任一标的的持仓市值不得超过权益的比例。
- **理由:** 随权益涨跌自动伸缩，不用维护多个绝对阈值；与 A-2a 的估值口径同源
  （同一套 `value_portfolio`），不需要新的取数路径。
- **边界:** 权益是**下界**（有持仓取不到价时不计入），因此这个比例可能被**高估** ——
  方向偏保守（更容易拦），但要知道偏差方向。

### ADR-029: 回撤基准是全历史峰值，触发后需显式重置

- **决策:** 权益回撤的峰值取**权益快照表的全历史最高值**；触发后**不会自愈**，
  必须显式重置（复用 `AgentConfigRepository` 存 `drawdown_reset_at`，峰值只看该时刻之后）。
  回撤触发时**清空全部持仓、回现金**。
- **理由:** 语义是"这套策略该停了"，与 PRD 的"回撤上限 5%"同义 —— 那是目标级判据，
  不是一个每天重来的日内指标。半途清一半没有依据：回撤是账户级信号，不是某个标的的问题。
- **代价（明说）:** 需要人工恢复。这既是代价也是特性 —— 全自动系统里，
  "停下来"必须是一个需要人确认的动作。它也是阶段 C 对话层"重开一局"的挂载点。
- **已知偏差:** 权益快照从 A-2a（2026-10-11）才开始记，所以**峰值窗口一开始很浅**，
  上线后头几天这道理序几乎不会触发。这是可达信息里的诚实做法，不臆造历史峰值。
- **否定方案:** 日内峰值（UTC 零点重置）→ 被否，与 `DailyLossRule` 语义重叠
  （一个相对开盘、一个相对日内高点），两者会互相遮蔽。

### ADR-030: 回撤重置有两个入口，且必须写明理由

- **决策:** 回撤重置同时提供 **HTTP** (`POST /api/v1/risk/reset-drawdown`) 与
  **CLI** (`python -m agent.risk reset-drawdown --reason "..."`)，两者调用同一个
  `reset_drawdown()`。**理由（`reason`）是必填**，且重置会写一条 `risk_events`
  （`event_type=drawdown_reset`，带重置前后的峰值与回撤）。
- **理由:** ADR-029 把"停下来"定成一个需要人确认的动作，那就得有一条能确认的路。
  HTTP 是无人值守（阶段 E）与对话层（阶段 C）的挂载点；CLI 是本地排障与
  "进程都没起来"时的唯一出路 —— 只留 HTTP 的话，API 挂了就没人能恢复；
  只留 CLI 的话，阶段 E 没人敲命令。
- **代价（明说）:** 同一个危险动作有两个入口，两处都要有测试，
  且两处的语义必须完全一致 —— 不一致比少一个入口更糟。
- **为什么 reason 必填、为什么写事件:** 重置是**唯一能让回撤线松开**的操作。
  仓库在 ADR-027 已经立过规矩：绕过闸门必须留痕，不做隐式放行。一个能静默
  解除风控的函数，等于给"永远不再触发"留了后门。`risk_events` 里那一行
  （谁在什么时候、为什么把峰值挪到了当下）就是这条后门的记录。
- **否定方案:** 只在 `agent_config` 写一个时刻、不记事件 → 被否，见上。
  未填理由时若默默接受 → 被否，`reset_drawdown()` 直接抛 `ValueError`。

### ADR-031: 行情上下文全量内联入库，不留引用

- **决策:** 每笔决策把**完整的**行情上下文（ticker + 指标 + 全部 K 线）原样写进库里，
  不做摘要、不做引用式存储。
- **理由:** R2 的原文是"**完整**留存，不是摘要"，而"不是摘要"这句话是有针对性的 ——
  现状恰好就死在这里（`summarize_market_for_log()` 只吐 `"BTCUSDT last=12345"` 一行）。
  更关键的是**引用回放不出来**：决策时的 K 线取自 Demo 交易所，行情库的 bar 来自
  生产 REST（ADR-013），**是两个源**。只存 symbol + 时间窗，事后拿行情库去回放，
  得到的不是模型当时看到的那份数据 —— 那样 R2 只是名义满足。
- **代价（明说）:** 实测 5.7 KB/笔（K 线占 93%），默认 tick 下**每年 0.57 GB**。
  保留期与归档策略见 §8 第 7 条，阶段 D 无人值守前必须定。
- **否定方案:** K 线存引用、其余内联 → 被否，见上（回放对不上）。
  只存技术指标不存原始 K 线 → 被否，指标是我们算的，K 线是交易所给的；
  事后要复核"指标算得对不对"，得先有原始输入。

### ADR-032: 对话层以 HTTP 端点为主，CLI 只做薄壳

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 阶段 C 的多轮会话挂在 HTTP 上（`POST /api/v1/chat` 一类的端点，
  按 session 承载上下文），CLI 只是一层薄壳，**不各写一套逻辑**。
- **理由:** ADR-022 要求验收给出"可复制的命令序列"——HTTP 端点天然满足这个。
  更实际的是：阶段 E 的**通知出口**要往同一批状态上挂，那时候需要一个
  进程外能到的入口，只做 CLI 的话得再补一层。
- **代价（明说）:** 端点一多，就得回答"谁能调"。PoC 阶段没有鉴权，
  这一点要写进 README，不能让人以为它是个能暴露的服务。
- **否定方案:** 只做 CLI → 被否，见上（阶段 E 要重做）。

### ADR-033: 目标的"初始资金"以激活时的实际权益为准

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 目标里记两个字段：`stated_capital`（用户口述的数字）与
  `baseline_equity`（目标转 `active` 那一刻的实际权益）。**"离目标还差多少"、
  收益率一律按 `baseline_equity` 算**；口述数字只在复述时用于校验，
  对不上就问一句，不悄悄采用任何一个。
- **理由:** ADR-024 已经把持仓与权益定成"以交易所为准，账本只解释变动"。
  拿用户口述的 1000 当基数，算的是一个**不存在的账户** —— 而"离目标还差多少"
  正是这个模块存在的理由（§2.2）。顺带：这也让 `baseline_equity` 天然成为
  回撤口径的起点，与 ADR-029 的峰值同源。
- **代价（明说）:** 两个字段可能长期不一致（用户说 1000、账户里 850），
  文档与界面必须让这个不一致**看得见**，而不是取其一。
- **否定方案:** 只用口述数字 → 被否，见上。只用实际权益、不记口述 → 被否，
  那样就丢掉了"用户以为自己在拿多少钱试水"这条信息，而它恰恰是复盘时要的。

### ADR-034: 目标解析——数字走确定性抽取，语义交模型

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 自然语言 → `GoalDraft` 分两层：**金额、百分比、时长**（回撤上限、
  收益目标、时间窗这类）用确定性抽取；**语义部分**（标的怎么选、要不要授权
  自主决策）才交模型。
- **理由:** 两条都成立才这么定。（1）**数字错了是硬错**：模型把"最多亏 5%"
  读成 5 倍，没有任何下游能拦住它 —— 而风控线正是最经不起读错的那个数。
  （2）**语义没法用规则**："我想稳一点"、"你看着办"这类话抽取不出来，
  硬做等于把 ADR-020 的"自然语言为主"缩水成一堆表单。
- **代价（明说）:** 两层之间要有明确的**分界**，而分界本身就是一处要维护的地方；
  且确定性那层只认几种说法，说得刁钻了仍然要回落到模型。
- **否定方案:** 全交模型 → 被否，见上（数字可靠性 + 每提一次目标就出网花钱）。
  先全确定性、完全不碰模型 → 被否，等于放弃 ADR-020。

### ADR-035: 风控强平认领到目标，但标记来源

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 某目标的持仓被风控强制平掉时，这条记录**记上 `goal_id`**，
  同时带 `origin="risk_force_close"`，与 LLM 决策产生的记录区分开。
- **理由:** 这是 §6.3 明确留下的待决项。强平是账户级巡检（ADR-027），
  本身确无 LLM 判断 —— 但"这个目标最后是怎么结束的"是归因时**第一个要问的问题**
  （R1）。不认领的话，链在这里断掉，而那恰恰是最需要解释的一段。
  标记来源是为了不让"强平"被读成"经理决定的"—— 这两件事的归因路径完全不同。
- **代价（明说）:** `goal_id` 这一栏从此有两种来源，读的人必须看 `origin`
  才知道它意味着什么。
- **否定方案:** 保持 `None` → 被否，见上（链断在最要命的地方）。

### ADR-036: 用户说的回撤上限与配置里的，取更紧的那个

- **状态:** ✅ 已采纳 | **日期:** 2026-10-11
- **决策:** 目标激活时，生效的回撤上限 = `min(配置里的 max_drawdown_pct, 目标里用户说的那个)`。
  用户没提就按配置。**两个数都存**：`goals.max_drawdown_pct` 是用户原话，
  风控快照里那个是实际生效值。
- **理由:** 这是写 C-1 时撞出来的 ADR-021 缺口 —— 它说"确认时固化、执行期间只读"，
  却没说过那两个来源谁说了算。取更紧的那个是唯一同时保住两件事的走法：
  用户能要求更严（说 2% 就按 2%），但不能一句话把系统设的闸门放宽 ——
  而后者正是 ADR-021 存在的全部理由（"风控一旦可被被约束者修改，它就不再是边界"）。
- **代价（明说）:** 用户说「亏到 5% 就停」而配置是 3% 时会**提前**在 3% 停。
  所以复述（§2.1 步骤②）必须把**生效值**讲清楚 —— 不说明白，用户就是照着一个
  不存在的前提在做决定。两列都留着，事后对一眼就知道当时是谁定的。
- **实现上的一条硬要求:** 快照**在 `activate()` 里现算**，不接受调用方递一份
  现成的字典进来。这类规则怕的是被绕过而不是写不出来 —— 调用方哪天忘了带上
  用户那个数，规则就静默失效，且失效的表现是**风控被放宽**，不是报错。
- **否定方案:** 用户说的覆盖配置 → 被否，见上（能让用户放宽闸门）。
  两者不一致就拒绝激活 → 被否，最保守但每提一次目标都可能被拒，
  且用户看不出该改哪边。配置为准、用户说的只作记录 → 被否，
  那样用户说的「最多亏 5% 就停」在风控上完全不生效，而复述里说了生效
  就等于在骗人。

### 承接的原有不变量

上述决策**不改变**以下既有约束：
- ADR-006：风控是 Execute 的唯一前置，无旁路 —— 经理层不得绕过
- ADR-013：行情取实盘，交易走 Demo
- 数据面独立（ADR-017）：本模块只通过供数接口与之相接

## 9. 术语

| 术语 | 含义 |
|------|------|
| 目标（Goal） | 用户提出的一段有判据的交易意图，含初始资金、收益目标、回撤上限、时间窗 |
| 经理 Agent | 理解目标、分解任务、指挥子 Agent 并判断进度的 LLM 编排者 |
| 子 Agent | 被经理调用的确定性执行单元（行情 / 分析 / 风控 / 执行） |
| 对话层 | 承载用户与经理多轮交互的通道与会话边界 |
| 会话（Session） | 一个目标的完整生命周期的载体，含消息、任务与状态 |
| 计划（Plan） | 经理对目标的一次分解结果，可被批准、执行、修订 |
| 控制面 / 数据面 | 分别指决策执行链路 / 行情采集加工链路（沿用行情模块术语） |
| 可归因性 | 任取一笔历史交易，能完整回答"为什么 / 当时看到什么 / 当时手里有什么"（ADR-019，R1–R3） |
| 硬性终止条件 | 由代码而非 LLM 判定并强制的目标终止判据：回撤触顶 / 时间窗到期 / 预算耗尽 |
