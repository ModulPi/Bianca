## 2. 峰值 QPS 估算

### 2.1 REST API 请求来源

| 请求类型 | 频率 (单用户 PoC) | 频率 (100 DAU) | 说明 |
|----------|-------------------|----------------|------|
| 策略状态查询 | 1 次/10s | 100 次/10s = 10 QPS | 前端轮询 |
| 持仓查询 | 1 次/10s | 10 QPS | 前端轮询 |
| 交易记录查询 | 1 次/30s | 3 QPS | 用户查看历史 |
| K 线数据查询 | 按需 | 5 QPS | 用户切换图表 |
| 策略配置 CRUD | 偶发 | 1 QPS | 创建/修改策略 |
| 健康检查 | 1 次/30s | 忽略 | Prometheus |

**PoC 峰值 QPS：** < 5（可忽略）  
**100 DAU 峰值 QPS：** ~30（非常低）

### 2.2 关键瓶颈分析

FnAgent 的瓶颈**不在 HTTP 请求**，而在以下方面：

| 瓶颈 | 详情 | PoC 影响 | 后期影响 |
|------|------|----------|----------|
| **WebSocket 行情流** | 每个交易对 1 条流，K 线更新 1-2 次/秒 | 低（10 交易对） | 中（200 交易对 = 200-400 msg/s） |
| **LLM 推理** | Ollama 单次推理 2-10s | 低（无 LLM） | 高（定时分析阻塞 GPU） |
| **订单 API 限流** | 币安 50 次/10s | 低 | 中（200 策略并发时需排队） |
| **数据库写入** | 每笔交易 1 条 + 风控事件 | 极低 | 低 |

### 2.3 WebSocket 消息量估算

```
单交易对 K 线流 (1m): ~1 msg/s (每秒更新)
10 个交易对: ~10 msg/s
200 个交易对: ~200 msg/s

单消息大小: ~300 bytes (JSON)
10 对带宽: ~3 KB/s
200 对带宽: ~60 KB/s
```

## 3. 数据增量估算

### 3.1 核心数据表增长

#### 交易日志 (trade_logs)

| 场景 | 日均交易 | 单条大小 | 日增量 | 年增量 |
|------|----------|----------|--------|--------|
| PoC (1 用户, 网格) | 20 笔 | ~500 B | 10 KB | 3.6 MB |
| 100 DAU (活跃) | 200 笔 | ~500 B | 100 KB | 36 MB |
| 1000 DAU (乐观) | 2000 笔 | ~500 B | 1 MB | 365 MB |

#### K 线数据 (klines - TimescaleDB 超表)

| 场景 | 交易对 | 时间框架 | 日行数 | 日增量 (未压缩) | 日增量 (压缩 10x) | 年增量 (压缩) |
|------|--------|----------|--------|-----------------|-------------------|---------------|
| PoC | 10 | 1m | 14,400 | ~3 MB | ~0.3 MB | 110 MB |
| 100 DAU | 50 | 1m | 72,000 | ~15 MB | ~1.5 MB | 550 MB |
| 1000 DAU | 200 | 1m | 288,000 | ~60 MB | ~6 MB | 2.2 GB |

#### 分析报告 (analysis_reports)

| 场景 | 日生成报告 | 单条大小 | 日增量 | 年增量 |
|------|-----------|----------|--------|--------|
| PoC | 1 次/天 | ~2 KB | 2 KB | 0.7 MB |
| 100 DAU | 10 次/天 | ~2 KB | 20 KB | 7 MB |

### 3.2 总存储需求

| 阶段 | 数据量 (1年) | 推荐配置 | 含 30% 缓冲 |
|------|-------------|----------|-------------|
| **PoC** | ~115 MB | 10 GB SSD | — |
| **100 DAU** | ~600 MB | 20 GB SSD | — |
| **1000 DAU** | ~2.6 GB | 50 GB SSD | — |

> **结论：** 交易系统的数据量极小（无图片/视频/日志），存储不是瓶颈。TimescaleDB 压缩后 K 线数据仅占 ~2GB/年（1000 DAU 级别）。

## 4. 服务器配置建议

### 4.1 PoC 阶段（个人自用）

| 资源 | 最低配置 | 推荐配置 | 说明 |
|------|----------|----------|------|
| CPU | 2 核 | 4 核 | Ollama 推理需要 CPU |
| 内存 | 4 GB | 8 GB | Ollama 7B 模型 ~4GB + 系统 |
| 磁盘 | 20 GB SSD | 50 GB SSD | 系统 + 数据 + Docker 镜像 |
| 网络 | 10 Mbps | 50 Mbps | WebSocket 行情流 |

**月成本：** 自用电脑即可运行，无需云服务器。若用云：
- 阿里云 ECS 2c4g：~¥100/月
- 或 Hetzner CX22 (2c4g)：~€4/月

### 4.2 100 DAU

| 资源 | 推荐配置 |
|------|----------|
| CPU | 4 核 (至少 2 核给 Ollama) |
| 内存 | 16 GB (Ollama 8GB + 服务 4GB + Redis 2GB + OS) |
| 磁盘 | 100 GB SSD |
| 网络 | 100 Mbps |

### 4.3 1000 DAU

| 资源 | 推荐配置 | 说明 |
|------|----------|------|
| CPU | 8 核 | 4 核 Ollama + 4 核服务 |
| 内存 | 32 GB | Ollama 用更大模型时需更多 |
| 磁盘 | 200 GB SSD | + 日志轮转 + 备份 |
| 网络 | 200 Mbps | |
| GPU | 可选 (T4/L4) | 加速 LLM 推理，不是必须 |

### 4.4 为什么不推荐 GPU 优先

- 7B 模型在 CPU 上推理 2-10s，对于**非实时**分析报告已够用
- GPU 显著增加成本（最低 ¥500+/月）
- 后期如果追求更快推理再考虑 GPU

## 6. 扩展路径

```
PoC (现在)          MVP (1-3月)           V1.0 (3-6月)          V2.0 (6-12月)
┌──────────┐      ┌──────────┐         ┌──────────┐          ┌──────────┐
│ Docker   │ ──→ │ 单机      │  ──→    │ 主从      │   ──→   │ 微服务    │
│ Compose  │      │ 单实例    │         │ PostgreSQL│          │ K8s       │
│ 单机     │      │ 单 DB     │         │ + 只读副本 │          │ 自动扩缩  │
└──────────┘      └──────────┘         └──────────┘          └──────────┘
  QPS: <5           QPS: ~30             QPS: ~300              QPS: 1000+
  数据: MB级         数据: GB级            数据: 10GB级            数据: 100GB级
```

每个阶段的瓶颈不同：
- **PoC → MVP**：瓶颈在功能完整性（合约、多策略、LLM 分析）
- **MVP → V1.0**：瓶颈在多用户并发 + 数据库读（加只读副本足够）
- **V1.0 → V2.0**：瓶颈在 Ollama 推理（需独立 GPU 节点或云端 LLM API）

## 7. 风险评估

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 币安 API 限流导致交易失败 | 中 | 高 | Token Bucket 限流器 + 指数退避重试 |
| WebSocket 断连丢失行情 | 高 | 中 | 自动重连 + REST 兜底拉取 |
| Ollama 推理超时阻塞 | 中 | 低 | 异步非阻塞 + 超时取消 + 降级跳过 |
| 数据库磁盘满 | 低 | 高 | TimescaleDB 自动压缩 + 数据保留策略 + 告警 |
| 内存不足 (Ollama + 服务) | 中 | 中 | 监控内存 + Swap 配置 + 降级用小模型 |
